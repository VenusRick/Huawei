### 0.3 本轮只保留一条正式主线

```text
训练、验证PCAP＋标签
        ↓
现有解析器／会话管理
        ↓
统一观测与特征计算
        ↓
现有筛选器＋直接学习规则的决策树
        ↓
规则文件＋特征定义＋分析报告
        ↓
独立进程加载规则，重新读取待识别PCAP
        ↓
同一观测与特征计算 → 严格规则匹配 → 预测与命中依据
        ↓
评价器只读取预测文件和独立真值
```

这里有两个产品入口，但只有一份解析、一份特征实现、一套标签、一套规则语义和一份最终指标实现。

具体决定：

1. 保留 `PCAPReader`、`SessionManager`、`BasicFeatureExtractor`、`AdvancedFeatureExtractor`、`FeatureSelector`、`OptimizedRuleGenerator`、`OptimizedDPIEngine` 和现有CLI所在文件。
2. 把 `tests/test_generic_pipeline.py` 中可用的流程搬入正式服务；该脚本改为薄包装，不再独立训练、计算特征或评价。
3. 第一版正式规则学习采用现有决策树路径提取代码。让树直接学习真实标签，再导出同一棵树，不从XGBoost“解释”出另一棵树后声称等价。
4. XGBoost保留在原文件或离线对照函数中，不强制迁目录。它可用于现有筛选器和效果对照，但其预测不进入正式DPI结果。
5. 原统计规则、哈希词袋等代码保留为显式实验开关；未校验的混合策略不默认启用。暂不增加GNN、Path Signature、神经FSNID、LLM代理、硬件后端。
6. 多流能力只扩展统一特征输入，不另设图分类支路。

**CART是先打通产品的实现选择，不是承诺它必然满足比赛精度。先得到可信规则基线，再根据同任务验证结果决定是否扩展规则学习器。**

## 1. 交付如何对应赛题

赛题明示六项核心功能。按[Q]第二部分逐项对齐：

| 赛题功能 | 本项目位置 | 必须展示的结果 |
|---|---|---|
| 加密协议解析与会话重建 | 现有parser/session；复用本轮修复 | TLS、QUIC和私有TCP/UDP样本可处理；乱序、重传不破坏统计及可见字段 |
| 基础特征提取 | `BasicFeatureExtractor`＋共享特征定义 | 导出带名称、单位、含义的特征；训练和识别计算一致 |
| 高级维度提取与生成 | `AdvancedFeatureExtractor`＋流段/窗口关系 | 流段交互、先后、重叠、相对传输量等显式特征，能在新PCAP上重算 |
| 智能总结并生成规则 | 筛选器＋同一决策树＋报告 | 自动给出可用特征、取值条件、行为规则及适用范围；不是只有重要性排名 |
| 可解释、严谨的规则引擎 | `OptimizedDPIEngine` | 全部AND条件满足才命中；缺失、阈值、拒识和冲突处理明确 |
| 高效运行并输出结果 | `dpi_infer`＋成本测试 | 规则包独立加载；输出标签、命中条件与性能数据 |

识别任务包括应用类型、精细化动作、匿名工具。配置可以把场景归成若干组，但项目自己的“七场景”不是官方固定类别总数。应覆盖题面列举的应用及行为，并记录各项数据是否具备。[Q]列举Facebook、X/Twitter、Instagram发文字帖；微信、WhatsApp文字聊天、语音通话、视频通话；Tor、Psiphon、Session工具流量。

跨平台指这些识别任务在Android、iOS、PC流量上的适应性，不是Python脚本能在三种操作系统启动。[Q]第三部分还要求：特征维度输出有效率80%以上、人工修正后可用率90%以上；召回率≥98%、准确率≥95%、精确率≥95%、假阳率≤5%。

上述比例的详细统计口径及DPI吞吐/时延门槛未在题面给出。工程验收采用本文明确的内部口径；正式比赛口径单独配置，不自行给官方增加Macro-F1或10Gbps门槛。

## 3. 五项接口契约：先统一这些，再接主入口

### 3.1 数据清单与标签

使用JSONL。路径相对于清单所在目录解析；允许用户已有数据只读软链。训练清单只含train/val，独立识别清单不带真值。

```json
{"capture_id":"cap01","pcap_path":"pcaps/cap01.pcap","group_id":"recording01","split":"train","label_id":3,"label_scope":"capture_trial","task":"behavior","entity_selector":{"ip":"192.0.2.10"},"platform":"android","app_version":"recorded-version","annotation_path":null}
```

上例为字段示意，不是已有数据。实际PCAP哈希由程序计算。`entity_selector`只负责指定可见终端，不作为分类特征。

`labels.json`使用显式结构，不按下划线拆应用名称：

```json
{"schema_version":1,"labels":[{"id":3,"app":"example_im","behavior":"text_chat","tool":null},{"id":7,"app":null,"behavior":null,"tool":"example_tool"}],"unknown_id":-1}
```

要求：

- ID 0也是普通合法类别，不自动等于背景，不允许跳过。训练库内部若需连续编号，维护双向映射。
- 验证、测试只能查冻结词表，不重新编号。[R]R27在此关闭。
- `capture_id/group_id/path/platform/app_version`只作溯源、分组和评价，不混入训练特征。
- 先按采集组划分，再派生flow、流段和窗口。复制PCAP或同一次操作产生的窗口不跨集合。
- `label_scope`必须区分文件级受控操作、应用级、流级、事件级。只有应用标签的数据不能自动升级为发文字、语音或视频标签。
- 背景是有真值的非目标流量；unknown是识别器的拒识结果；两者不是一个概念。未标注流量也不能自动当背景。
- 测试目标类在训练中没有样本时，记为未覆盖目标／未知测试类，不偷偷补进训练。

**处理现有sample_debug：** 保留其多格式、小文件用途。先检查每类独立采集组数量。一类仅一个PCAP且没有其他独立采集证据时，不通过随机flow拆分生成正式泛化指标。可以跑提取、训练、规则加载的调试冒烟；正式指标换成满足分组条件的数据。数据不足不阻塞合成全链路验收，也不允许编造应用标签。

### 3.2 统一观测，不让训练看到推理拿不到的信息

第一里程碑沿用单流输入，先做 `flow_prefix`。第二里程碑补 `entity_window`。二者只是同一服务的观测配置，不是两条算法主线。

`ObservationSpec`至少保存：模式、前缀包数/观察时长、窗口长度/步长、流段划分参数、方向定义、终端选择策略、流过滤策略。

`FeatureRecord`至少包含：

```text
observation_id, capture_id, entity_id, start_time, end_time,
features, validity, quality_flags, feature_spec_version
```

`features`与元信息分开。`observation_id`不依赖标签，训练侧和独立引擎能生成同一个ID。

- 前缀取前N个捕获事件时，持续时间、包数、方向统计、载荷范围全部来自该前缀；不沿用完整session的end_time。[R]R30。
- 特征函数不得更改原session.packets、payload或累积计数。连续调用结果应相同。[R]R24。
- 包统计采用明确的捕获事件口径。TCP按SEQ重组字节供TLS使用，但不能把SEQ排序当真实到达时间去计算IAT或burst。
- 过滤逻辑只有一份。短流、解析失败或证据不足应有状态，不得在训练与识别各自静默丢弃不同样本。
- 窗口边界由流量及配置生成，不读应用真值、事件名称或测试目录名。

### 3.3 特征定义和缺失值

`FeatureSpec`记录特征名、单位、公式/计算函数、观察范围、适用协议、缺失原因、数值转换及所依赖算子。只有规则真正使用的特征进入部署计划。

先修[R]R16/R22：

- 短流、长流按相同schema输出；不可计算的统计使用明确缺失状态。
- 有观测依据的“次数为0”可为0；“未抓到握手”“协议不适用”“解析异常”不可都伪装成观测值0。
- 必需字段整列未产生，或bundle引用不存在的特征，是schema错误，不静默补0。
- 对正常、可预期的缺失值，可以使用显式训练集拟合的填补策略和缺失指示项，但必须保存到bundle，训练与运行采用相同转换。禁止推理时临时`features.get(name, 0)`。
- 某可选协议字段不可见时，应允许不依赖该字段的规则继续工作，不因一个可选字段缺失而使所有普通TCP/UDP统计失效。
- 所有输入尺度、类别编码、NaN处理、float精度都保存在bundle，不由推理CLI另行决定。

训练和推理共用：

```python
iter_observations(input_manifest, observation_spec)
extract_record(observation, feature_spec)
encode_record(feature_record, fitted_preprocessing)
```

Agent自行确定返回类型，但必须有类型注解、错误状态和一致性测试。

### 3.4 规则包

继续把 `rules.yaml` 作为人可读入口。为避免只拿到YAML却缺运行配置，统一交付一个小目录：

```text
bundle/
  rules.yaml                  # 实际条件、规则/树结构、标签映射与决策策略
  feature_spec.json           # 特征、变换、缺失策略、实际计算依赖
  observation.json            # flow_prefix或entity_window的完整定义
  bundle_meta.json            # 版本、来源run_id、各文件哈希、训练依赖版本
```

第一版所有模型判断都必须能由这些文件描述。pickle、XGBoost模型文件不属于正式规则推理必需品。普通运行时库如NumPy、YAML和协议解析依赖允许保留；“独立”不等于“零依赖”。

规则语义：

- 路径条件是AND；同一类别可以由多条独立路径覆盖。
- `<=`和`>`分别保留，不四舍五入后改变边界；所有有效类别叶子都导出。
- 特征值存在但等于0，不满足`not_exists`。缺失相关运算符优先于数值转换处理。
- 规则为空、引用未知算子或必要版本不兼容，加载时失败，不等到运行时变unknown。
- 默认没有神经网络或XGBoost回退。规则不命中或低于冻结阈值，输出unknown及原因。
- 决策树原始路径互斥；若后续人工修改造成不同标签规则同时命中，采用bundle中显式策略。第一版默认`unknown/conflict`，不取YAML偶然第一条。
- 叶子样本分布可作为分数来源，但不是已校准正确概率。原始分数、阈值和决策结果分开记录。

先验证**原树→导出规则**一致性，再验证阈值及人工修改。树推理的类别由`classes_`映射，输入转换和并列决策按训练库已记录语义复现；不依赖当前机器另一个版本默认值。[W4]

### 3.5 最终预测和评价

识别输出JSONL，每个观测至少包含：

```text
observation_id, capture_id, entity_id, start_time, end_time,
status, predicted_label_id, app, behavior, tool,
score, rule_id, reason, matched_conditions, bundle_id
```

`status`最少为`matched/unknown/invalid`；unknown原因区分`no_match/low_score/conflict/insufficient_evidence`。全部状态保留。命中依据包含实际特征值、比较符、阈值和适用窗口，不是另一个模型的SHAP解释。

Evaluator只接收独立预测文件和真值，不能访问训练分类器重新预测。[R]R23/R29。

已知类c：`TP_c`为正确接纳c；`FN_c`包含被分到其他类及被拒识的真实c；`FP_c`为其他类别/背景/未知被判为c。Precision、Recall、F1据此计算。Accuracy分母为预先确定的完整有效评价样本集合，不能随接纳阈值改变。

处理失败单独报比例；在端到端识别成功率中计为未正确完成。文件损坏、没有合法真值等不可评价项在评价前定义并报告数量，不能根据预测结果删样本。

报告必须区分：全部样本指标、接纳覆盖率、接纳子集指标。后者可辅助分析，不能用来选出“只接纳少量容易样本”的部署阈值。用验证集最终规则预测选择阈值，随后冻结。没有阈值同时达标时，记录未达项，保留验证结果最合理的候选，不打印全部达标。

## M1：正式挖掘、独立识别和真实评价连成一条链

### 修改范围

优先关闭未修项R25/R28/R26、R16/R22/R24/R30、R18—R21/R31、R27/R23/R29。不是等它们全部逐项写完报告后再联调，而是围绕下面的端到端测试迭代。

### 规则学习最小实现

保留现有筛选器作为可关闭步骤，提供`selection=none`对照。先用小范围验证选择树深、叶子样本数、剪枝参数；不要固定要求树一定极浅。最大树深可从4/6/8开始比较，这些是开发候选，不是验收门槛。

每个训练阶段：训练数据拟合预处理、选择器、树；验证数据选配置和拒识阈值；测试数据只通过最终独立引擎一次性评价。若报告交叉验证，预处理与选择必须在各折内重新拟合，按采集组拆分。

`_traverse_tree`使用该树`classes_`映射全部叶子，输出置信度所需分布及准确阈值。不要在生成器硬编码丢弃0类或固定0.7过滤，再在引擎使用另一阈值。[R]R20/R21/R31。

### M1验收

- 先用小型合成PCAP集合完成无mock正式CLI三阶段：mine、独立detect、evaluate。合成集合至少有两类和多个独立采集组；训练、验证、测试文件不同。
- 程序生成一个新bundle，而不是读取旧 `output/results/rules.yaml`；输出路径必须为本轮新目录。
- 独立识别进程只拿到运行时代码、bundle、待测PCAP及终端映射，不拿到标签、训练特征或模型文件。
- 删除复制测试环境中的`model.pkl/model.json`，或安装不含训练库的独立运行环境，规则识别仍可启动；用新进程而非内存中的旧classifier。
- 同一PCAP在训练侧共享提取与独立推理提取的`observation_id`、特征值、缺失状态相同。
- 原树与导出后规则在测试数值、真实特征样本、阈值两侧样本上结果一致；测试包括ID 0、非连续类ID、概率并列和正常缺失路径。[W4]
- “100个已知样本只正确接纳20个”用例，Recall与端到端正确率均不能被报告成1。全拒识时目标类Recall为0。
- 正式输入错误不得自动产demo；推理发现schema不兼容必须明确失败。

M1结果文件：`bundle/`、`predictions.jsonl`、`metrics.json`、`e2e.log`、`parity.json`。真实任务数据不足时，用合成样本验收接口正确性，用真实PCAP验收输入处理，不虚构业务成绩。

## M2：让同一条链处理精细化行为，而不只是单流应用分类

### 为什么要补这一层

赛题要求精细行为识别。[R]只证明了现有单流调试流程与R17聚合修复，没有提供新版本多流关联的实现/验证证据。此前方案已确定多流关系只作为高级特征；本轮沿用该决定，不加入图网络。

### 实现方法

1. 在现有逐包入口增加事件转发能力，供 `context.py` 聚合。不能等所有FlowSession关闭才构建当前行为窗口，否则持续通话无法按窗口输出。
2. 按`capture_id＋可见终端`维护有限时间窗。首版沿用现有5秒窗、1秒步长作为候选默认值，保存进bundle；后续只用验证数据调节。
3. 窗内每条连接按活动间隔分流段。流段保存自身起止时间、所属连接、上下行量及包序列引用。连接和流段方向都相对于选定终端，不跨连接用“谁先发包”混作上行。
4. 同一窗口允许多条连接，直接从对应包计算汇总统计；不要平均各流均值代替全窗口加权统计。
5. 初版高级特征只做三组：
   - 窗内连接/流段数量、方向变化、活动与空闲时间；
   - 单流段上下行占比、包长分布、持续时间等；
   - 流段之间的时间间隔、重叠长度/比例、是否不同连接、相对字节量。
6. 可使用固定槽位降低实现成本：选择按起始时间排序的前K个流段，K初始为3；时间相同时按首个捕获包序号排序。缺槽位有有效性标记。窗口总量统计仍使用全部纳入窗口的包，不因只展示K个槽位漏计。
7. `seg0/seg1`是明确绑定的同一对流段。关系特征和节点特征必须来自相同槽位；不得把“某段满足A”和“另一不相关对满足先后关系”拼成一个虚假的交互模式。
8. 所有特征按第3节共享接口输出，再由原规则学习器训练。引擎只需按相同配置计算这些标量，不新增图匹配器或状态机语言。

固定槽位是首版实现选择，不能声称能天然消除背景噪声。若首段背景通信频繁影响性能，再在验证集比较槽位数/候选规则，不先引入复杂局部图搜索。

### 观测与标签一致

训练和检测使用完全相同的窗口生成器。行为日志在窗口生成后用于标注，而不是用真实动作时间替运行时生成更“干净”的窗口。

先使用受控、标签明确的行为试次验证。例如一个真实IM应用的文字聊天、语音通话、视频通话及非目标活动。各动作必须确有数据，不能把语音消息改名成语音通话。

对连续采集流量，动作时间区间与窗口标签的映射规则写入评价配置。持续通话可按窗口评价；短时操作还应按事件评价，否则一次消息被多个重叠窗口重复计分。事件命中采用同终端、正确标签和预先固定的时间容差进行一对一匹配；同一事件重复告警不能产生多个TP。事件指标不用于替代需要真负例分母的窗口FPR。

同时出现多个真实动作而当前输出仅单标签时，记录重叠数量并说明可评价范围；不通过修改真值强行选一个。先完成单动作＋背景条件，再扩展明确的多标签能力。

### M2验收

- 相同单流统计、不同跨流先后/重叠结构的合成例，产生预期不同关系特征。
- 两个终端各有一半模式，不得被合并成一个完整模式。
- 同一长连接跨多个窗口时，各窗只使用本窗可见信息，不用未来包；窗口在配置截止时即可产出。
- 将包分不同读取批次输入，结果相同；同捕获时刻相同的稳定排序确定。
- 多次累计窗口结果能够对应到真实PCAP与动作记录，训练/识别不读取目录类名作为输入。
- 至少一个拥有真实行为标签的子任务完成M1同样的mine→独立detect→evaluate；没有真实行为标签时提交具体缺数据项，但不能只建空的行为类。
- 输出应用、行为和工具使用同一结构化标签体系；应用级数据和工具数据仍可走同一条规则链的flow配置。

M2结果文件：`behavior_feature_spec.json`、`behavior_bundle/`、行为预测、分行为结果和可追溯命中示例。已达到M1的功能不回退。

## M3：完成“智能分析工具”的产品输出与人工修正规则

本阶段不是增加AI模型，而是让用户看见并使用挖掘结果。[Q]要求智能总结识别维度、生成规则，并考察人工修正后可用率。

### 自动分析报告

复用已有 `_save_reports`、`save_all_features`、`generate_feature_definitions` 和规则摘要输出。统一生成：

- 特征目录：名称、层次、公式/单位、缺失含义、计算成本及哪些规则使用它。
- 按类别对比的统计：目标类、最易混淆类别、选中/剔除原因。不只输出全体均值或模型重要性。
- 规则列表：完整条件、标签、训练支持样本数/独立组数、验证命中数/误命中数/漏检数、分平台表现。
- 可行识别方案：例如“先检查哪些低成本条件，再计算哪一组关系；何时拒识”。从实际规则模板化生成即可，不要求LLM。
- 命中样例和误判样例：关联原观测ID、时间范围和条件值，方便人工修正。

“选中60/319个特征”是保留比例，不是特征有效率。工具不能通过改列名把这两个比例混在一起。[C]原mine和旧特征有效性输出需要同步改正。

### 人工修正最小流程

CLI支持读取规则编辑JSON（或用户修改后的YAML），更改区间、启停规则、选择既有合法特征。修改后校验运算符和特征依赖，在验证集回放，输出相对旧bundle的效果差异；确认发布时生成新版本，不覆盖原bundle。

新增原来未部署的特征条件时，同步更新计算计划；未知函数或任意Python表达式禁止进入规则文件。无需开发图形界面。

### 特征有效性/可用性记录

官方细则未给出时，保留可审查原始表，不自称官方验收。工具至少记录每个自动输出候选维度的：可计算性、定义一致性、验证集判别证据、引擎支持情况、人工判定和修改内容。

输出“自动输出维度集合、自动确认有效集合、人工修正后确认可用集合及各自数量”。报告比例必须说明分母和判定规则，不把阈值调优自动记成人工确认；无法判断的条目保留pending。

### M3验收

- 从新一次 `mine` 自动产生说明、特征报告、规则报告，而不是手工填模板。
- 改一条规则后，新bundle在独立引擎中的命中结果确实改变；旧bundle仍可复现。
- 提交不支持特征、无效区间或冲突编辑时，明确拒绝或给出冲突结果。
- 报告所有统计来自同一次run对应的bundle和预测，不拼接历史文件。
- 新增一类少量样本可通过清单和标签配置重新学习，不需要在引擎内手写应用名称判断分支。

## M4：性能、任务覆盖与比赛交付

### 特征按需计算

优先把特征分成少量算子组（基础计数、IAT、载荷统计、握手、流段关系），通过bundle引用解析计算依赖。先允许一个组内一起计算，但必须实测减少了哪些组的调用。不能只在全部特征计算完成后删列。

独立引擎按文件块读包、按流/窗口更新状态并输出；已关闭会话、已过期窗口和TLS缓存释放。上线前有配置上限：活跃会话、单方向重组字节、流段数、待输出队列；达到上限产生可统计的截断/不足证据状态，不伪装完整统计。

性能测试分开记录：文件读取＋解析＋特征＋匹配的整体吞吐，匹配本身耗时，峰值RSS，活跃状态峰值，平均/P95计算时延，以及观察窗口造成的等待时间。PCAP存储字节吞吐与网络原始字节吞吐口径分开，不拿小包样本和大包样本混比。

与“同规则、计算全特征”比较，验证按需计划是否降低成本且标签/分数相同；同时报告规则数、条件数、实际使用特征数。没有官方性能门槛时，交付实测值和配置，不自行承诺10Gbps。

### 真实数据与场景矩阵

建一张任务清单，至少覆盖题面列举的三类任务。每行记录应用、具体动作/工具、平台、独立训练/验证/测试采集组数、是否含非目标背景、标签来源、最终指标和缺口。

优先把已有数据中**标签与任务相符**的子集接入；再补缺少的题面行为与平台。不把不同来源的任意类别混合后得到的均值当题面识别成绩。

小样本试验以独立行为试次/采集组为预算单位，例如每类5/10/20次；记录实际能够提供的档位和学习耗时。每次操作产生很多flow不等于提供了很多独立标注行为。

跨平台至少分别报告Android、iOS、PC上的效果。联合训练后分平台测试与留出平台测试分开命名；留出平台属于进一步泛化证据，不把题面适应性要求悄悄改成“必须零样本跨平台”。不具备对应平台数据时列缺口，不能拿其他平台改名。

### 比赛交付件

按[Q]第四部分，最后交付：

1. 挖掘工具和独立规则引擎源代码，包含运行依赖、配置和接口。

3. 引擎技术说明书：规则格式、特征定义、判断与拒识语义、资源和性能。

5. 标注数据集及清单、平台信息、划分和标签说明；受提供方限制的数据按授权可交付范围说明，不假装随源码完整交付。

## 5. 已修16项的处理：保留，集中补联合测试

不重新推倒parser。导入原33项回归用例，再补三组跨模块用例；这三组集中检验已有修复能否支撑全链路，不另起长期协议研究。

### 5.1 TCP统计与TLS字节重组联合用例

[R]R03展示了按SEQ补乱序缓冲；R12展示了一个TLS record按顺序分两段后可恢复SNI。它们不能单独证明两层接起来也正确。

构造同一个ClientHello的完整、分段、乱序、重复段、部分重叠版本，并包含一个握手消息跨多个TLS record的版本。期望：完整可重组版本提取相同可见字段；捕获事件不双计；未补齐缺口不能凭后到数据拼造完整握手；四元组复用不串联旧TLS缓存。TCP负责可靠有序字节，TLS记录与握手消息边界还需各自处理。[W1][W2]

另查双向FIN及最终ACK后是否生成伪新会话；截断结束时按既定关闭策略记录。没有握手的中途抓包使用“首个观测方向”，不能无依据称为真实发起方。

### 5.2 GREASE判定精确性

[R]R14写出的 `(v & 0x0F0F) == 0x0A0A` 会把 `0x1A2A` 也判为GREASE；而RFC8701的16位GREASE值不是所有低半字节均为A的组合。[W3]

建议直接用精确集合，限定对应的16位字段：

```python
GREASE_16 = frozenset(0x0A0A + 0x1010 * i for i in range(16))

def is_grease_16(value: int) -> bool:
    return value in GREASE_16
```

测试全部16个值，以及0x1A2A等反例。不要把8位point format列表当16位扩展列表过滤。本包 `reference/report_predicate_probe.json` 仅复算报告中的表达式，不是对新源码的调用证据。

### 5.3 QUIC成功识别与降级路径同时验证

R10修的是异常不丢UDP，不等于已经完成QUIC协议能力。至少配套一个有效QUIC输入、一个短头/未知版本输入和一个普通UDP反例。比较总UDP包数、有效协议字段、不能解析字段的状态。

首版协议能力应明确支持的QUIC版本，验证长头版本/连接标识/边界。要展示QUIC握手特征，就在对应版本Initial上完成去头保护、Initial解保护及CRYPTO重组后调用共享TLS握手解析器，或集成经过验证的现成解析组件；不能直接把密文当TLS正文扫描。RFC9001定义Initial保护及测试向量。[W5]

只提供版本和连接标识时，报告就写该可见范围，不把缺失握手一律填0后声称已完成握手分析。私有TCP/UDP协议继续提供通用重组、长度和时序描述，不要求解密私有应用内容。

这三组可与M1/M2联调并行，正式宣称协议完整支持前必须通过相应范围测试。

## 6. 目标CLI与端到端验收命令

```bash
# 0. 检查清单、独立采集组、任务标签与源文件；不修改数据
python -m src.pipeline --mode validate-data \
  --manifest data/task/train_val.jsonl --task behavior

# 1. 正式挖掘，只读取训练/验证资料
python -m src.pipeline --mode mine \
  --manifest data/task/train_val.jsonl \
  --task behavior --config configs/competition.yaml \
  --output output/run001

# 2. 新进程：测试输入清单无真值，加载规则而非训练模型
python -m src.engine.dpi_infer \
  --rules output/run001/bundle/rules.yaml \
  --input-manifest data/task/test_inputs.jsonl \
  --output output/run001/inference/predictions.jsonl

# 3. 评价只读真值和最终预测，不再传入clf或X_test
python -m src.pipeline --mode evaluate \
  --truth data/task/test_truth.jsonl \
  --predictions output/run001/inference/predictions.jsonl \
  --output output/run001/evaluation

# 4. 人工修正后的验证与新版本输出；不能读取封存测试数据调参
python -m src.pipeline --mode revise-rules \
  --rules output/run001/bundle/rules.yaml \
  --edits review/edits.json \
  --manifest data/task/validation.jsonl \
  --output output/run001_revision

# 5. 一键工程验收（需由Agent实现，不是本包现有脚本）
python scripts/run_acceptance.py \
  --config configs/acceptance.yaml --output output/acceptance001
```

`python -m src.pipeline --mode detect --rules ... --input ...`可继续作为兼容入口，但内部必须调用同一独立识别服务。旧`tests/test_generic_pipeline.py --data ...`可以继续作为debug入口，不得维护第二套业务流程。

各命令输出路径存在时，默认要求新run目录或显式覆盖许可；不能覆盖旧结果再引用旧hash。失败返回非零并保存失败步骤。

### scripts/run_acceptance.py必须做什么

不是顺序调用几个命令后打印PASS。至少检查：

- 正式mine退出0且生成本轮非空有效bundle。
- 独立推理进程退出0，输出观测数量与输入范围能够核对。
- 识别进程没有读取测试真值、训练特征或模型文件。
- 原树与规则、离线与独立特征两项一致性均通过。
- 每个预期评价样本恰有一条结果；重复、丢失、非法类别明确失败或按已定义状态记入。
- 指标能从预测文件单独复算，阈值与bundle一致。
- 改变目标规则后结果随之变化；恢复规则后结果恢复，证明运行时真正使用规则文件。
- 启用按需计算后没有执行未依赖算子组，输出不变。
- 按里程碑返回结果：`PASS/FAIL/BLOCKED_DATA`，三者不能混成单个成功提示。
