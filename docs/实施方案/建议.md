这版路线已经基本成型。主干是对的：

**M1 工程底座 → M2 行为级观测 → M3 智能分析与规则修订 → M4 性能与比赛交付。**

需要改的不是方向，而是几个会影响最终收口的问题。

第一，**P0不要演变成大规模重构**。`data_manifest.py / features/runtime.py / evaluation.py / reporting.py`都可以建，但定位应是给现有代码加统一契约，不要重新实现解析、特征公式和规则逻辑。整个工程最好只维护下面这一条数据链：

```text
Manifest
   ↓
Observation
   ↓
FeatureRecord
   ↓
RuleBundle
   ↓
Prediction
   ↓
Evaluation / Report
```

应用识别、精细行为识别、匿名工具识别都走这条链。区别只存在于 `task config + manifest + feature spec + rule bundle`。这样后面不会变成三套系统。

第二，**M2里的多流行为特征必须仍然是FeatureRecord的一部分**。`context.py`只负责把包组织成“终端窗口—连接—流段—关系”，不能另起一个Enmob式分类器。Enmob值得借鉴的是“行为由多个流及其时序关系共同组成”，不是它完整的图匹配算法。论文明确把单流统计和flow间先后、共现关系结合起来描述行为。

建议把M2输出固定成：

```text
Observation
├── window features
├── segment_0 features
├── segment_1 features
├── segment_2 features
└── relation features
```

然后继续进入现有：

```text
feature selection → CART/rule learning → RuleBundle → DPI
```

不要再新增Graph Model、GNN、DTW匹配等旁路。

第三，**K=3可以作为首版工程限制，但不要写成方法假设**。应该定义：

```yaml
context:
  max_segments: 3
  ordering: start_time_then_first_packet_index
  overflow:
    aggregate_remaining: true
```

即前三个关键流段保留槽位，剩余流段仍进入窗口级统计。否则真实行为有4条以上连接时信息会被静默丢掉。

第四，也是当前计划最大的缺口：**真实行为数据不能长期停在 `BLOCKED_DATA`。**

比赛明确要求应用类型、精细化动作和匿名工具流量识别，并且要求Android、iOS、PC平台适应性，同时最终还要交付标注数据集。

因此建议在P1后面强制增加：

### P1.5：比赛数据构建

不要把 `WAN_WATCH / VOICE / Recording` 这种文件名前缀直接当正式行为真值。没有明确动作时间和采集过程时，只能记为 `candidate_label`。

正式清单至少包含：

```json
{
  "capture_id": "...",
  "trial_id": "...",
  "platform": "android|ios|pc",
  "device_id": "...",
  "app": "...",
  "app_version": "...",
  "behavior": "...",
  "behavior_start": 0.0,
  "behavior_end": 0.0,
  "network_env": "...",
  "pcap": "...",
  "label_source": "ui_event|automation|manual_verified"
}
```

优先采集题目直接要求的场景，例如：

```text
IM
├── text
├── voice call
└── video call

Social
└── post text

Anonymous
├── Tor
├── Psiphon
└── Session
```

F3L最值得借鉴的不是Android实现本身，而是：

**动作事件 → 时间戳 → 时间校准 → 流量窗口标签。**

它明确指出用户动作、网络流量生成和UI标签出现之间存在时间差，所以需要校准标签时间，而不是看到UI变化后直接切PCAP。

Android可以用Accessibility/ADB/Appium记录事件；PC可以用自动化脚本或人工事件记录器；iOS如果暂时难以自动取UI事件，可以用AP侧抓包＋独立动作记录器。三端最终都转换成同一种manifest即可。

第五，**数据划分必须在P0就写死**：

```text
trial/capture group → train / validation / test
```

然后再产生窗口。

不能：

```text
一个行为试次
↓
切成20个窗口
↓
随机分到train/test
```

否则同一次行为的连续窗口会泄漏。

建议规定：

```text
同一 capture_id / trial_id 永远不能跨集合
同一设备的一次连续采集不能拆分
平台留出实验单独配置
```

第六，M3整体设计对，但建议把“智能分析工具”的输出归一成**一个 AnalysisPackage**，而不是很多零散报告：

```text
analysis/
├── feature_catalog.json
├── feature_effectiveness.csv
├── class_profiles.json
├── confusion_analysis.json
├── rules_explained.json
├── misclassified_samples.jsonl
├── recognition_plan.md
└── report.html
```

核心展示逻辑统一成：

```text
为什么这个行为可以识别
        ↓
哪些特征有区别
        ↓
选择了哪些特征
        ↓
形成了哪些条件组合
        ↓
这些条件如何变成DPI规则
        ↓
在哪些样本上成功/失败
```

这比单纯做SHAP图更符合赛题。赛题要求的是“智能总结可用特征维度和可行识别方案”，最终还要生成规则。

第七，**特征有效率需要现在就固定口径**。你已经意识到：

```text
selected_features / all_features
```

不是特征有效率。

建议工程内部先定义：

```text
自动输出特征 A
        ↓
可正确计算
        ↓
训练/推理定义一致
        ↓
验证集存在判别证据
        ↓
可被规则引擎使用
        ↓
自动确认有效 E
```

则：

$$
EffectiveRate=\frac{|E|}{|A|}
$$

人工修订后再得到集合 \(U\)：

$$
UsableRate=\frac{|U|}{|A|}
$$

同时把每个特征的判定原因留档。这样即使后续赛事方给出更具体统计口径，也容易转换。

第八，**P3的按需计算应放在行为规则稳定之后再做。** Traffic Refinery的核心结论正是：不能只看特征数量，要看state、processing、storage等实际系统成本，而且不同表示的性能—成本关系并不线性。

因此最终依赖链建议设计成：

```text
RuleBundle
   ↓
required_features
   ↓
required_operators
   ↓
runtime activates only required operators
```

例如：

```text
Rule #12
├── duration
├── fwd_bytes
└── segment_overlap_ratio
```

则runtime只打开：

```text
basic_counter
segment_tracker
relation_tracker
```

不要计算319维后再取3维。

---

最后建议把整个计划正式收敛成 **5个阶段**：

| 阶段          | 目标                | 必须产物                                        |
| ----------- | ----------------- | ------------------------------------------- |
| **P0 M1+**  | 把现有M1变成可长期维护的统一底座 | manifest、runtime schema、evaluate、acceptance |
| **P1 M2**   | 增加窗口、流段、流间关系      | behavior FeatureSpec、合成行为测试                 |
| **P1.5 数据** | 获得真正的精细行为真值       | Android/PC/iOS行为试次manifest与PCAP             |
| **P2 M3**   | 自动分析特征并形成可修改规则    | AnalysisPackage、revise-rules、新RuleBundle    |
| **P3 M4**   | DPI优化、正式测评、交付     | 性能报告、任务矩阵、五件套                               |

P4继续作为穿插的协议回归即可，不应该成为独立研发线。

最终系统架构可以稳定成：

```text
                        ┌──────────────┐
PCAP + Action Log ─────▶│ Data Manifest │
                        └──────┬───────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │ Traffic Processing  │
                    │ session / TLS / QUIC│
                    └─────────┬───────────┘
                              │
                              ▼
              ┌───────────────────────────────┐
              │ Unified Feature Runtime       │
              │ basic / temporal / segment    │
              │ / cross-flow / protocol       │
              └──────────────┬────────────────┘
                             │
                    offline  │
                             ▼
              ┌───────────────────────────────┐
              │ Intelligent Feature Analysis  │
              │ selection + pattern discovery │
              │ + rule learning               │
              └──────────────┬────────────────┘
                             │
                             ▼
                        RuleBundle
                             │
              ┌──────────────┴───────────────┐
              │                              │
              ▼                              ▼
       Analysis Report                Independent DPI
                                             │
                                             ▼
                                        Prediction
                                             │
                                             ▼
                                         Evaluate
```

这条线和赛题是完全对齐的：**复杂分析留在离线特征挖掘工具，在线端保持简单规则执行。**

当前计划可以开始执行。唯一建议作为硬性调整加入Agent计划的是 **P1.5真实行为数据构建**。否则代码可以全部完成，但到比赛收口时仍然缺“精细化行为”和“跨平台”最核心的证据。
